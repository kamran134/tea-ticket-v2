# Контекст: UX-редизайн схемы выбора мест (2026-09-01)

## Что не меняем
Backend, Prisma, API, `cart.ts`, правила `toggleSeatInCart`, цены, статусы `occupied`.
Покупка по-прежнему: клик по месту → корзина в `RegisterForm` → `POST /api/tickets/register`.

## Где живёт визуал
- Покупатель: `VenueGridMap` (fullscreen overlay) + новые `components/seatmap/*`.
- Админский `GridMapEditor` не редизайним — общий только `GridCanvas`/`TableIcon`.
- Легаси `SeatPicker` / `TablePicker` (зоны вне сетки) не трогаем, кроме согласованных цветов если пересечёмся.

## Визуальный язык
Шапка/подвал сайта уже тёмные (`#0a0a0a`, акцент `#d4af37` BIR MANAT BAND).
Схема покупателя — тёмная event-карта, не неоновая игра:
- сцена — gold;
- выбрано — emerald (`#059669`), как CTA/корзина;
- категория — цвет зоны на обводке свободного места;
- занято — muted + перечёркивание (не только цвет).

## Zoom
Не canvas-rewrite. `GridCanvas` масштабирует CSS `transform: scale(zoom)` вокруг уже существующей CSS-grid раскладки. Pan = native overflow scroll. Pinch и ctrl+wheel. Кнопка reset. `fitCols` работает и на mobile, чтобы сначала была видна вся схема (сцена как ориентир), затем zoom in для тапа.

## CTA при пустом выборе
Continue **остаётся активным** при пустом выборе: Cancel восстанавливает snapshot корзины, а Done фиксирует текущий (в т.ч. очищенный) выбор. Иначе пользователь не сможет подтвердить «убрать все места».

## E2E контракт
`data-testid="seat-*"`, `data-seat-status`, `data-testid="map-selection"`, `title` на GENERAL-клетках (`QA General`), кнопки Купить/Готово.

# Контекст: Сетка как основной инструмент продажи мест

## Задача
До этой задачи в проекте были две несвязанные системы:
- «Схема» (`ZoneMapEditor`/`VenueMap`) — реально привязана к `Zone.layoutData`, использовалась
  при покупке билета.
- «Сетка» (`GridMapEditor`) — черновик-калькулятор поверх `Venue.gridLayout` (один JSON на
  зал), зоны в нём — отдельный тип `GridZone`, не связанный с `Zone` в БД. В покупке билета
  не участвовала.

Пользователь решил: «Схема» пока не нужна в менеджменте (скрыть вкладку, код оставить).
«Сетка» должна стать реальным механизмом — и для рисования зон, и для выбора места при
покупке билета. Плюс нужна поддержка зон без конкретных мест (просто вместимость, билет
продаётся «в зону», не на место) — уже наполовину есть на бэке как `ZoneType.GENERAL`.

## Ключевые решения

### Архитектура сетки
- Сетка остаётся на уровне всего зала: `Venue.gridLayout = { rows, cols, cells }`.
- Ячейка — `'empty' | 'blocked' | <реальный Zone.id>`. Отдельного типа `GridZone` больше нет.
- Для `SEATED`-зон: закрашенная ячейка = реальный `Seat`. Координаты ячейки переиспользуют
  существующие поля `Seat.row` (= grid row) и `Seat.posInSection` (= grid col), `sectionIndex`
  всегда `0`. Модель `Seat` не меняется — только семантика полей для зон, рождённых из сетки.
- Для `GENERAL`-зон: закрашенная область — только визуальная граница, `Seat` не создаются.
  Вместимость — отдельное число, вводится вручную, НЕ обязано совпадать с количеством ячеек
  (пользователь: «не заморачиваемся с точным счётом»).
- В `Zone` добавлено `color String?` — для покраски на сетке (раньше цвет был только у
  ад-хок `GridZone`).

### Синхронизация мест при сохранении сетки
- `PUT /api/venues/:id/grid-layout` в одной транзакции: для каждой затронутой `SEATED`-зоны
  считает желаемый набор ячеек, сравнивает с существующими `Seat`, удаляет лишние/добавляет
  новые. Если у места, которое нужно удалить, есть активный билет (`BOOKED/PENDING/CONFIRMED`)
  — вся операция отклоняется с 409 (нельзя стереть уже проданное место).
- После синхронизации `capacity` зоны пересчитывается как реальное количество мест —
  аналогично существующему `POST /api/zones/:id/generate-seats`.

### GridMapEditor теперь работает с реальными зонами
- При открытии подгружает зоны венью через `api.getZones` (а не только из `gridLayout`) —
  значит зоны, созданные в старой вкладке «Зоны», тоже можно красить на сетке. Зоны типа
  `TABLE` в сетке не участвуют (у них своя логика столов, не про клетки/места).
- «+Зона»: создаёт реальную зону сразу через `api.createZone` — с чекбоксом «Без конкретных
  мест» (снят → `SEATED`, отмечен → `GENERAL` + поле «Вместимость»). Для `SEATED` capacity
  при создании — плейсхолдер (пересчитается при первом сохранении сетки).
- Удаление зоны с чипа — реальный `api.deleteZone`, с обработкой 409 (если уже есть билеты).

### Покупка билета
- `RegisterForm` теперь предпочитает сетку (`VenueGridMap`, новый компонент) над старой
  «Схемой» (`VenueMap`, приоритет ниже, для обратной совместимости) и карточками (fallback).
- `SeatPicker` менять не пришлось: он и так рендерит места по `row`/`sectionIndex`/
  `posInSection` — для зон из сетки `sectionIndex` всегда 0, получается обычная 2D-сетка мест.

### «Схема» — скрыта, не удалена
- В `ManagePanel.tsx` вкладка `'map'` убрана из списка табов, JSX-блок и компоненты
  `ZoneMapEditor`/`VenueMap` остаются в коде нетронутыми.

## Новые файлы

## Ограничения
- Нельзя стереть ячейку/место (или стол — см. Этап 39), если на нём уже
  активный билет (409, откат всей транзакции)
- Нельзя удалить зону, если у неё есть билеты (409, FK-конфликт перехватывается явно)

## Окружение разработки (важно для последующих раундов)
- В этой рабочей директории **нет Docker** и локального PostgreSQL — `docker-compose.dev.yml`
  существует, но поднять его здесь нельзя. Проверка ограничивается
  `tsc --noEmit` (backend + frontend) и `vite build`; реальный UI-сценарий
  (клики, отправка формы, ответы API) проверяется только после деплоя на
  проде (`tea-ticket.com`) — см. паттерн проверки в остальной части этого файла
  и `plan.md`. Явно сообщать об этом ограничении пользователю при подведении
  итогов, а не молчать о том, что UI не протестирован вживую.
- `npx prisma generate` (без БД) достаточно, чтобы типы `@prisma/client`
  подхватили изменения `schema.prisma` для чистого `tsc --noEmit` бэкенда —
  делать это после любой правки модели, до typecheck.

  «На весь экран» — теперь видна всегда
- Маска телефона — намеренно не привязана к конкретной стране (нет единого

## Этап 39 (2026-08-02): сцена + столы на сетке
- `'stage'` — не зона, просто зарезервированное значение ячейки (как
  `'empty'`/`'blocked'`), поэтому не проходит через `zones`-массив ни на
  фронте, ни на бэке — везде явные точечные проверки `cell === 'stage'`
- Столы: раньше `type: TABLE` зоны были жёстко запрещены на сетке
  (`venues.ts` кидал 400) и жили только через bulk-эндпоинт
  `POST /api/zones/:id/generate-tables` с плоским списком без координат.
  Теперь красятся на сетке как обычная зона, каждая ячейка = один `ZoneTable`
  (`row`/`col`), синхронизация 1:1 с тем, как `Seat` синхронится для SEATED
- `ZoneTable.row`/`col` — **nullable намеренно**: старые столы, созданные
  через `generate-tables` до этой фичи, остаются с `row=null` и НИКОГДА не
  участвуют в grid-sync-диффе (см. `plan.md`, Этап 39, известное ограничение) —
  это осознанный компромисс, чтобы не тронуть/не удалить существующие
  проданные столы на проде задним числом
- `generate-tables` эндпоинт **оставлен в бэке**, просто из UI больше не
  вызывается — тот же принцип "спрятать, не удалять", что и для старой
  вкладки «Зоны» в `ManagePanel`
- `Zone.tableChairs` — обязателен только для `type: TABLE` (`zod .refine`),
  для остальных типов всегда `null` (не `undefined` — фронт обязан слать
  явный `null`, т.к. `Zone.tableChairs` в типах непустое поле `number | null`)

## Этап 40 (2026-08-02): мебель для столов (footprint вместо 1 клетки)

Этап 39 сделал 1 клетка = 1 стол (по образцу SEATED-мест). Пользователь
после этого попросил визуально красивую мебель (круг/прямоугольник/диван
со стульями вокруг) — физически не влезает в одну клетку, поэтому Этап 40
меняет модель на "стол = прямоугольная область из нескольких клеток".

- `ZoneTable.row/col` теперь означают верхний левый угол области, а не саму
  клетку (в отличие от Seat, где row/col — это ровно клетка). `rows/cols` —
  размер области. Всё это персистится в БД именно так, чтобы `VenueGridMap`
  на фронте мог строить карту клика без пересчёта — просто читает
  `table.row..row+rows` × `table.col..col+cols`
- Размещение стола на сетке — НЕ drag-paint (в отличие от всех остальных
  инструментов), а дискретный клик-стемп: `tryPlaceFootprint` проверяет, что
  вся прямоугольная область пуста, иначе toast и отмена. Причина: попытка
  красить многоклеточный объект перетаскиванием мыши даёт неопределённое
  поведение (наложения, частичные штампы) — проще и предсказуемее "один клик
  = один стол"
- Симметрично: стереть можно только весь стол целиком одним кликом (flood
  fill по связной области), НЕ одну клетку — иначе на сетке остаётся дыра,
  которая не проходит серверную валидацию "область обязана быть сплошным
  прямоугольником" (`findTableBlobs` возвращает `null` → 400 при сохранении).
  `handleCellMouseEnter` (drag) в `GridMapEditor` явно игнорирует клетки
  стола — их нельзя случайно затереть протаскиванием другого инструмента
- `TableIcon.tsx` — общий компонент (SVG), используется и в `GridMapEditor`
  (админ, до сохранения — просто рисует по живым `cells`), и в `VenueGridMap`
  (покупатель — рисует по сохранённым `ZoneTable.row/col/rows/cols` из БД).
  Источники позиции разные (live-грид vs персистентные данные), но сам
  SVG-рендер идентичный
- `tableFootprint(shape, chairs)` — тиры размера footprint'а не завязаны на
  точное число стульев линейно (иначе стол на 20 человек занял бы половину
  сетки) — количество нарисованных точек-стульев капается на 10, дальше
  просто перестаёт расти визуально; РЕАЛЬНОЕ число мест всё равно берётся
  из `zone.tableChairs`/`table.chairCount`, точки — чисто декоративные
- `TableShape.SOFA` — добавлено значение в существующий Prisma enum
  (`ALTER TYPE ... ADD VALUE`, отдельной миграцией, без использования нового
  значения в той же транзакции — стандартное ограничение Postgres для enum)

## Merge master → bank-emulation (2026-08-05)

Ветка `bank-emulation` добавляет платёжный шлюз, истечение броней и отправку
билетов через email. В `master` параллельно появились security/audit-фиксы,
единый Prisma-клиент, ESLint и новый общий frontend renderer.

При разрешении конфликтов сохраняются обе группы изменений:
- payment/email routes и фоновые jobs остаются в `createApp`;
- `createApp` использует общий Prisma-клиент и middleware из master
  (`helmet`, `trust proxy`, закрытая статическая раздача чеков);
- публичные ticket endpoints скрывают контакты участников группы, но продолжают
  возвращать статус email-доставки;
- небезопасный upload receipt не восстанавливается, admin использует
  авторизованный endpoint чтения;
- frontend сохраняет оплату и email-статусы, используя `PublicTicket` и общий
  `renderApp`.
