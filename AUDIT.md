# Аудит tea-ticket-v2 — 2026-08-02

Разбор всего кода (7.3k строк src). Общая карта проекта — в [CLAUDE.md](CLAUDE.md).

**Как читать.** Каждая находка: `ID` · где · что сломано · как чинить. Приоритеты:
`P0` — ломается прямо сейчас у пользователя; `P1` — сломается при нагрузке/злом умысле;
`P2` — техдолг, стоит денег при каждой правке; `P3` — гигиена.
Всё, что помечено **проверено** — я воспроизвёл логику по коду, а не предположил.

Общая оценка: код заметно выше среднего для хобби-проекта — единый формат ответов API,
zod на входе, транзакции в критичных местах, осмысленные комментарии «почему». Основные
проблемы: (1) сетка зала продублирована между редактором и витриной и уже разъехалась,
(2) грабли вокруг групповых билетов и столов, (3) отсутствие защиты от гонок и злого ввода
на публичных ручках, (4) мусор от прошлых итераций (S3, cron, легаси-табы).

---

## Топ-6, что чинить первым

1. **B1** — удаление главного билета группы ломает QR у всех остальных.
2. **B2** — «Сохранить как шаблон» падает всегда, если в зале есть столы или сцена.
3. **B3** — изменение «мест за столом» не доезжает до уже созданных столов; редактор и
   покупатель видят разные столы.
4. **B4** — тосты не отображаются нигде, кроме админки (`<Toaster/>` подключён в 1 из 4 точек входа).
5. **S1** — `quantity` в корзине ничем не ограничен → OOM бэкенда одним запросом.
6. **S3** — билеты можно купить на скрытое или уже прошедшее мероприятие.

## P0 — Баги

### B1. Удаление главного билета группы ломает QR у всех остальных · проверено
`apps/backend/src/routes/tickets.ts:350` · `apps/frontend/src/components/TicketView.tsx:176`

`groupId` группы равен id её первого билета. `DELETE /api/tickets/:id` удаляет строку без
оглядки на это. Если админ удалит главный билет, у остальных остаётся `groupId`, указывающий
на несуществующий билет. `TicketView` рисует QR как `ticket.groupId ?? ticket.id`, сканер
делает `GET /api/tickets/<groupId>` → 404 → «Билет не найден». Группа не пройдёт на входе.

**Фикс:** либо запретить удаление главного билета группы, пока есть другие участники, либо
при удалении переназначить группу: выбрать нового «главного» и переписать `groupId` у всех.
Правильнее — развязать связь: добавить отдельную модель `TicketGroup` (или просто
`groupId String @default(cuid())`, не равный id билета).

### B2. Шаблон сетки невозможно сохранить, если в зале есть столы или сцена · проверено
`apps/backend/src/routes/grid-templates.ts:13,73` · `apps/frontend/src/components/GridMapEditor.tsx:402-431`

Две независимые причины 400:
- `templateZoneSchema.type: z.enum(['GENERAL','SEATED'])` — фронт шлёт и `'TABLE'`
  (`GridMapEditor.tsx:411`).
- валидация клеток пропускает только `'empty' | 'blocked' | slotId` — клетка `'stage'`
  даёт `Unknown slot id in cells: stage`, хотя инструмент «Сцена» есть в редакторе.

Плюс, даже если тип разрешить: `tableChairs` / `tableShape` нет в zod-схеме, они молча
отбрасываются, и `applyTemplate` подставляет заглушки `4 / ROUND` (`GridMapEditor.tsx:451`).

**Фикс:** добавить `'TABLE'` в enum, добавить `tableChairs`/`tableShape` в
`templateZoneSchema`, добавить `'stage'` в белый список клеток. Валидацию клеток стоит
вынести в общий хелпер — она уже дублируется с `venues.ts:214` (там `'stage'` учтён).

### B3. Правка «мест за столом» / формы стола не доезжает до существующих столов · проверено
`apps/backend/src/routes/venues.ts:326-357` · `apps/frontend/src/components/VenueGridMap.tsx:419`

`chairCount` и `shape` копируются из `Zone` в `ZoneTable` **только в момент создания**
(`createMany`, `venues.ts:351`). Диффер сравнивает столы по якорю `row-col`: существующий
стол на том же месте не обновляется никогда. Итого после правки зоны:

- количество мест за столом в БД остаётся старым → продаётся неверное число стульев;
- редактор рисует стол по `zone.tableShape` (`GridMapEditor.tsx:1097`), а витрина — по
  `table.shape` (`VenueGridMap.tsx:419`) → **админ и покупатель видят разные фигуры**;
- `tableFootprint()` при смене количества мест даёт другой размер, а в БД лежат старые
  `rows/cols` → иконка перестаёт совпадать с кликабельной областью.

**Фикс:** в транзакции `grid-layout` добавить ветку «обновить существующие»:
`updateMany({ where: { zoneId, row: {not:null} }, data: { chairCount, shape } })` + обновление
`rows/cols` по новому footprint. Уменьшать `chairCount` ниже числа активных билетов за столом
— запрещать (409), как уже сделано для удаления. И выбрать один источник правды по форме
стола: либо всегда `ZoneTable`, либо всегда `Zone`.

### B4. Тосты не видны нигде, кроме админ-панели · проверено
`apps/frontend/src/manage.tsx:22` (единственный `<Toaster/>`) · `main.tsx`, `ticket.tsx`, `admin.tsx`

`TicketView.tsx:50` вызывает `toast.success('Ссылка скопирована — не потеряйте её!')` сразу
после покупки — сообщение не отрисуется никогда, потому что на `ticket.html` нет `<Toaster/>`.
Пользователь не узнаёт, что ссылка на билет скопирована в буфер.

**Фикс:** вынести общий шелл (`<StrictMode><Toaster/>{children}`) и использовать во всех
четырёх точках входа. Заодно унифицировать обработку ошибок: `RegisterForm` показывает ошибки
через локальный `error`-стейт, остальные — через тост.

### B5. Зоны со старой схемой пропадают, если в зале нарисована сетка · проверено
`apps/frontend/src/components/RegisterForm.tsx:93-99`

```ts
const hasSchemaZones = !hasGridZones && schemaZoneIds.size > 0;
const cardZones = zones.filter(z => ... && !schemaZoneIds.has(z.id));
```

Зона с непустым `layoutData`, не закрашенная на сетке, при наличии `gridLayout` не попадает
ни в карту, ни в карточки — её невозможно купить, и админ об этом не узнает.

**Фикс:** `cardZones` должен ловить всё, что не отрисовано ни одним из активных способов:
`zones.filter(z => !gridZoneIds.has(z.id) && !(hasSchemaZones && schemaZoneIds.has(z.id)))`.

### B6. Нумерация мест на сетке выглядит случайной
`apps/backend/src/routes/venues.ts:306`

`counter = max(существующий number) + 1`. Дорисовали ряд сверху — он получает номера больше,
чем ряды под ним. Покупатель видит «Место 47» над «Местом 3».

**Фикс:** после синхронизации перенумеровать все места зоны по `row, posInSection` одним
проходом. Осторожно: `@@unique([zoneId, number])` — либо во временный отрицательный диапазон,
либо `updateMany` в два прохода.

### B7. Прогон покупателя не проверяет legacy-места, сгенерированные по рядам
`apps/backend/src/routes/venues.ts:268-315`

Если зону, у которой места созданы через `generate-seats` (координаты 1-based), потом
закрасить на сетке (0-based), диффер посчитает все старые места «лишними» и удалит их;
при наличии активного билета — 409 с текстом про строку/колонку, которого админ не поймёт.

**Фикс:** минимум — понятный текст ошибки («у зоны есть места из старого генератора,
сбросьте их перед рисованием на сетке»). Максимум — миграция координат.

## P1 — Безопасность и устойчивость

### S1. Неограниченный `quantity` кладёт бэкенд · проверено
`apps/backend/src/routes/tickets.ts:154,159`

```ts
for (let i = 0; i < item.quantity; i++) slots.push(...)
```
`quantity` валидируется как `positive int` без верхней границы, а проверка вместимости идёт
**после** построения массива. `{"quantity": 100000000}` → OOM до единой проверки. Ручка
публичная, без авторизации и rate-limit.

**Фикс:** `z.number().int().min(1).max(50)` на `quantity`, `.max(20)` на `items`,
`.max(50)` на `seatIds` и `guestNames`. Дополнительно — общий лимит слотов на заказ.

### S2. Гонка → овербукинг для зон без мест и столов · проверено
`apps/backend/src/routes/tickets.ts:204,218`

Проверка «занято + запрошено ≤ вместимость» — это `count()` в транзакции на дефолтном
Read Committed. Два одновременных заказа оба проходят проверку и оба вставляют билеты.
Для `SEATED` спасает `Ticket.seatId @unique`, для `GENERAL` и `TABLE` защиты нет вообще.

**Фикс:** заблокировать строку зоны перед подсчётом —
`` await tx.$executeRaw`SELECT id FROM "Zone" WHERE id = ANY(${zoneIds}) FOR UPDATE` `` (и то же
для `ZoneTable`), либо `isolationLevel: 'Serializable'` + ретрай. Заодно поймать `P2002` по
`seatId` и вернуть 409 вместо нынешней 500.

### S3. Билеты продаются на скрытые и прошедшие мероприятия · проверено
`apps/backend/src/routes/tickets.ts:114-130`

`register` проверяет только принадлежность зон к `venueId`. Ни `venue.active`, ни `venue.date`
не проверяются. Страница `/e/:slug` для скрытого мероприятия отдаёт 404, но прямой POST
работает — а `venueId` виден любому, кто открывал страницу до скрытия.

**Фикс:** внутри транзакции `tx.venue.findUnique` и отказ, если `!active || date < now`.

### S4. `GET /api/venues?all=true` публичный
`apps/backend/src/routes/venues.ts:20-34`

Отдаёт скрытые и прошедшие мероприятия кому угодно, хотя используется только в админке
(`ManagePanel.tsx:112`). Утечка небольшая, но флаг явно админский.

**Фикс:** `all=true` — только с `requireAuth`.

### S5. Персональные данные и чеки доступны без авторизации
`apps/backend/src/routes/tickets.ts:38,61` · `apps/backend/src/index.ts:20`

- `GET /api/tickets/:id` и `/group/:groupId` публичные и отдают имя, телефон, email **всех**
  участников группы. Знание одного id раскрывает контакты всей компании.
- `/uploads` раздаётся `express.static` без проверок — загруженный чек (банковская выписка)
  лежит по предсказуемому пути `/uploads/receipts/<ticketId>/<timestamp>.<ext>`.

Ссылка-билет по сути и есть capability-URL, так что публичность самой ручки оправдана.
Но набор полей — нет.

**Фикс:** урезать публичный ответ (`name`, `zoneName`, `status`, `checkedIn`, `price`; телефон
и email — только под `requireAuth`); чеки отдавать через авторизованный роут вместо статики.

### S6. `POST /:id/upload-receipt` без авторизации и без владельца
`apps/backend/src/routes/tickets.ts:266`

Кто угодно, зная id билета, может залить файл и перевести бронь `BOOKED → PENDING`.
Единственный барьер — проверка статуса, то есть сработает ровно один раз на билет.

**Фикс:** раз онлайн-оплаты нет и UI загрузки чека у покупателя убран — удалить ручку целиком
(вместе с `multer` в `tickets.ts`). Если нужна — подписанный токен в ссылке.

### S7. Path traversal при загрузке постера/плана (нужен админ-токен) · проверено
`apps/backend/src/routes/venues.ts:391,411`

`key = \`posters/${req.params.id}/...\`` — `req.params.id` попадает в путь без валидации, а
Express декодирует `%2F`. `POST /api/venues/..%2F..%2F..%2Fetc/upload-poster` запишет файл
вне `UPLOADS_DIR` (запись произойдёт до падения `venue.update`). Требует токен админа, поэтому
не критично, но чинится в одну строку.

Отдельно проверил `key` из `originalname`: `split('.').pop()` по определению не может
содержать точку, так что `..` туда не протащить — **это не дыра**, но длина расширения
не ограничена.

**Фикс:** проверять существование venue до загрузки и/или гнать id через
`/^[a-z0-9]{20,32}$/`; расширение брать из `mimetype`, а не из имени файла.

### S8. Нет валидации env при старте
`apps/backend/src/middleware/auth.ts:17` · `apps/backend/src/routes/auth.ts:23`

`process.env.JWT_SECRET!` — если переменная не задана, `jwt.sign` бросает исключение внутри
хендлера (500 на логине), а `jwt.verify` валит все админские запросы в 401 «Invalid token».
Диагностировать по симптомам тяжело.

**Фикс:** zod-схема окружения в `index.ts`, падать на старте с внятным сообщением.

### S9. Нет rate limit на логин
`apps/backend/src/routes/auth.ts:7`

Один пароль на всю систему, брутфорс ничем не ограничен, попытки не логируются.

**Фикс:** `express-rate-limit` на `/api/auth/login` (например 10 попыток / 15 мин на IP),
`helmet()` на всё приложение. Учесть, что за nginx нужен `app.set('trust proxy', 1)`.

### S10. Протухший токен не разлогинивает
`apps/frontend/src/services/api.ts:5` · `ManagePanel.tsx:54`

`isTokenValid()` проверяется только при монтировании. Через 24 часа админка остаётся
«залогиненной», но все запросы молча возвращают 401 → пользователь видит только тост «Ошибка».

**Фикс:** в `request()` перехватывать 401 → чистить `admin_token` и перезагружать страницу.

## P2 — Архитектура и дублирование

### A1. Сетка зала реализована дважды и уже разъехалась
`GridMapEditor.tsx` ↔ `VenueGridMap.tsx`

Дословно продублированы: `ZoneBox`, `zoneBoundingBoxes`, `sameZoneNeighbor`, `zoneColor`,
палитра `FALLBACK_COLORS`/`ZONE_COLORS`, вся логика отрисовки клетки (цвета, слияние границ,
оверлеи имени зоны и сцены, позиционирование иконок столов). Расхождения, которые уже есть:
источник формы стола (B3), способ поиска зоны по клетке (`Map` против `findIndex`, см. P1),
подпись «осталось N» есть только у покупателя.

**Фикс:** вынести `components/grid/` — `GridCanvas` (чистая отрисовка по
`cells` + `zoneById` + рендер-проп на клетку), `gridGeometry.ts`
(`zoneBoundingBoxes`, `connectedBoxes`, `sameZoneNeighbor`), `zoneColors.ts`.
Редактор и витрина остаются только с обработчиками кликов.

### A2. Flood-fill написан трижды
`venues.ts:157 findTableBlobs` (бэк) · `GridMapEditor.tsx:73 connectedBoxes` (фронт) ·
`GridMapEditor.tsx:124 removeConnectedBlob` (фронт)

Один и тот же обход связных компонент по 4 направлениям. Бэкенд дополнительно требует
«сплошной прямоугольник», фронт — нет. Если фронт когда-нибудь позволит нарисовать
Г-образный стол, пользователь узнает об этом только по 400 при сохранении.

**Фикс:** общий модуль (`packages/shared` или дублированный, но одинаковый файл), и
проверка «сплошной прямоугольник» **в редакторе**, до сохранения.

### A3. Слаги — два несовместимых генератора
`apps/backend/src/services/slug.ts` ↔ `apps/frontend/src/utils/slug.ts`

Таблица транслитерации скопирована, но `generateVenueSlug` разный: бэк берёт
`date.toISOString().slice(0,10)` (UTC), фронт — `dateIso.slice(0,10)` из `datetime-local`
(локальное время). Для события в 01:00 по Баку предложенный в UI слаг и сгенерированный
бэкендом отличаются на день.

Отдельно: **нет азербайджанских букв** (`ə ğ ı ö ü ş ç`) — «Çay gecəsi» превращается в
`ay-gec-si`. Для бакинского проекта это заметно.

**Фикс:** один файл на два приложения, добавить азербайджанскую и турецкую латиницу,
дату форматировать явно (`toLocaleDateString('sv-SE')` или ручной `YYYY-MM-DD` по локали).

### A4. Пять экземпляров PrismaClient
`tickets.ts:8`, `venues.ts:17`, `zones.ts:6`, `grid-templates.ts:6`

Каждый открывает свой пул соединений (по умолчанию ~9 на инстанс) — до ~36 коннектов
к Postgres вместо одного пула. При `ts-node-dev --respawn` ещё и не закрываются вовремя.

**Фикс:** `src/db.ts` с единым синглтоном, импортировать везде.

### A5. Форма логина и `isTokenValid` скопированы
`ManagePanel.tsx:34-43,379-406` ↔ `AdminScanner.tsx:6-15,158-185`

Идентичные функция и JSX формы.

**Фикс:** `useAdminAuth()` + `<AdminLoginGate>{children}</AdminLoginGate>`.

### A6. `errMsg` заново пишется в каждом файле
`GridMapEditor.tsx:65` (функция), `ManagePanel.tsx:151` (стрелка), плюс inline
`err instanceof Error ? err.message : '...'` в `RegisterForm`, `ZoneConfigurator` (×3),
`ZoneMapEditor`.

**Фикс:** `services/errors.ts → errMsg(err, fallback)`.

### A7. `type Tool = 'block' | 'erase' | string` схлопывается в `string`
`GridMapEditor.tsx:14` — юнион с `string` не даёт никакой проверки. Дальше по коду
`activeTool` сравнивается со строками и с id зон, отсюда же ветвление вида
`cell !== 'empty' && cell !== 'blocked' && cell !== 'stage'`, повторяющееся ~8 раз.

**Фикс:** `type Tool = { kind: 'block' } | { kind: 'erase' } | { kind: 'stage' } | { kind: 'zone'; id: string }`
и хелпер `isZoneCell(cell)`.

### A8. Один зашитый админ и никакой аудитории действий
Один bcrypt-хеш в env; кто подтвердил или удалил билет — нигде не фиксируется. Для одного
организатора нормально, но при первом же помощнике станет проблемой. Зафиксировать как
осознанное решение или завести таблицу `AdminUser` + `AuditLog`.

## P3 — Производительность

### P1. `zones.findIndex` внутри отрисовки каждой клетки
`GridMapEditor.tsx:1005`

O(клетки × зоны) на каждый рендер. Сетка 50×50 и 10 зон = 25 000 сравнений, и это **на каждое
`mouseenter` при рисовании мышью** (перерисовываются все 2500 `div`). Витрина эту же задачу
решает через `Map` (`VenueGridMap.tsx:72`).

**Фикс:** `useMemo` с `Map<string, {zone,index}>`; вынести клетку в `React.memo`-компонент.

### P2. `RegisterForm` пересчитывает всё на каждое нажатие клавиши
`RegisterForm.tsx:85-110`

`zoneById`, `gridZoneIds` (полный обход `cells`), `cartQuantityBy*`, `cartTotal` считаются в
теле компонента без `useMemo`. Ввод имени/email перебирает всю сетку зала на каждый символ.

**Фикс:** обернуть в `useMemo`; форму контактов вынести в отдельный компонент, чтобы её
ререндер не трогал карту.

### P3. N+1 по HTTP при открытии карты
`VenueGridMap.tsx:95,133` · `RegisterForm.tsx:79`

По одному запросу `getSeats`/`getTables` на каждую зону, и `RegisterForm` грузит столы
повторно, хотя `VenueGridMap` уже сделал это сам.

**Фикс:** один публичный `GET /api/venues/:id/grid-data` → `{ venue, zones, seats, tables }`.
Убирает заодно мигание «Загрузка мест...» поверх уже отрисованной сетки.

### P4. Админка тянет все билеты и считает на клиенте
`ManagePanel.tsx:141,357` · `StatsTab.tsx:26`

`GET /api/tickets` без пагинации, счётчики по статусам и выручка считаются в браузере.
На пару сотен билетов нормально, на пару тысяч — нет.

**Фикс:** `GET /api/tickets?…&limit&offset` + отдельная ручка агрегатов (`groupBy` в Postgres).

### P5. Транзакция `grid-layout` — последовательные запросы по зонам
`venues.ts:267-369`

На каждую зону 3-4 запроса подряд внутри одной транзакции; дефолтный таймаут Prisma — 5 с.
Большой зал с десятком зон может упереться.

**Фикс:** собрать все `findMany` до цикла, `createMany`/`deleteMany` — пачками;
явно задать `{ timeout: 15000 }`.

### P6. Индексов не хватает
`schema.prisma:129-131`

`Ticket` индексирован по `groupId`, `status`, `[venueId,status]`. Но `groupBy(['tableId'])`
и `groupBy(['zoneId'])` в `zones.ts:25-46` идут без индекса по `zoneId`/`tableId`.

**Фикс:** `@@index([zoneId, status])`, `@@index([tableId])`.

## Мелочи, которые дёшево починить

- `.claude/settings.local.json` закоммичен и содержит IP продакшн-сервера и историю
  ssh-команд под `root`. Файл локальный — в `.gitignore`.
- `venues.ts:136` — любая ошибка в `PATCH /venues/:id` возвращает 404 «Venue not found»,
  включая падение БД.
- `api.ts:10` — `res.json()` без проверки `res.ok`: 502 от nginx превращается в
  `SyntaxError: Unexpected token '<'` в лице пользователя.
- Единицы `cqw` используются в 19 местах (`GridMapEditor`, `VenueGridMap`, `VenueMap`,
  `ZoneMapEditor`), но `container-type` не задан **нигде** — проверено. Размеры считаются
  от вьюпорта, а не от контейнера, то есть текст не масштабируется вместе с сеткой.
  Нужен `container-type: inline-size` на обёртке сетки.
- `zones.ts:83` — `capacity: z.number().int().positive()`, при этом `grid-layout` сам пишет
  `capacity: 0` для очищенной зоны. После этого зону нельзя сохранить из UI, пока не
  закрасишь клетки.
- `AdminScanner.tsx:105` — `lastScanRef` сбрасывается в `finally`, то есть защита от
  повторного скана не работает; спасает только `stopScanning()` сразу после скана.
- `AdminScanner.tsx:34` — при размонтировании `stop()` без `clear()`, камера может остаться
  занятой.
- `GridMapEditor.tsx:433` — `applyTemplate` создаёт зоны последовательными запросами; при
  ошибке на середине в БД остаются зоны-сироты с ценой-заглушкой `1`.
- `GridMapEditor.tsx:406` — в шаблон уходят **все** зоны мероприятия, включая незакрашенные.
- `GridMapEditor.tsx:239` — уменьшение размера сетки молча стирает закрашенное за границей.
- `ManagePanel.tsx:112`, `Afisha.tsx:797`, `RegisterForm.tsx:71`, `StatsTab.tsx:26` — `.then()`
  без `.catch()`: при ошибке сети экран остаётся в «Загрузка...» навсегда.
- `vite.config.ts` — нет `server.proxy` для `/api`, локальная разработка требует
  `VITE_API_URL` и открытого CORS.
- `formatPrice` живёт в `types/index.ts` — рантайм-функция в файле типов; перенести в `utils`.
